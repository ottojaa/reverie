## Entries

- `2026-11-21` — **Env booleans are strict, and photos never reach Claude vision.** Never use `z.coerce.boolean()` for a flag: it is `Boolean(value)`, so `LLM_VISION_ENABLED=false` read as true. `config/env.ts` has `envBoolean(default)`: `true/false/1/0` in any case, anything else (including an empty string) fails startup naming the variable; use it for every new flag (`z.coerce.number()` is fine, nothing treats 0 as a flag). The vision path is gated in `llm/llm.service.ts processDocument` through `llm/photo-gate.ts isHeldBackFromVision`, ahead of any forced type and after the private/trashed stops: an image is held back (job ends skipped, reason `photo`, `llm_status = 'skipped'`, no `llm_results` row) when `tools/photo.ts withholdsImageContent` says so (camera EXIF date/GPS in `photo_metadata`, or category `photo`) **or when its `document_category` is still null**, since uploads are unclassified until OCR runs and a directly queued job can arrive first. Only a classified non-photo image (screenshot, graphic, ...) reaches `describeImage`. Gap: `photo_metadata` keeps only date and GPS, so camera EXIF without either is caught only by the `photo` category.
- `2026-11-21` — **Embeddings (pgvector + `reverie-ml` + `embed-queue`) gotchas.** (1) Postgres stays Alpine/musl: `docker/postgres/Dockerfile` builds pgvector onto the pinned `postgres:16.x-alpine3.y`; never switch to the Debian `pgvector/pgvector` image (glibc over a musl-made data dir silently changes collation). Build it with `with_llvm=no OPTFLAGS=""`: the Alpine server is configured with LLVM, so PGXS otherwise tries to emit bitcode and fails. (2) BullMQ rejects `:` in custom job ids, and `queue.add` with a job id that still exists is silently dropped, so the backfill (`embed-backfill`) reschedules the same job with `updateData` + `moveToDelayed` + `throw new DelayedError()` rather than adding a successor. (3) Jobs added with a `priority` sit in `prioritized`, not `waiting`: queue-busy checks must count `getJobCounts('waiting','prioritized','active')` (`isPipelineBusy`). (4) The repo's `NonRetryableJobError` does not stop BullMQ retries; use `UnrecoverableError` for a final failure (an undecodable image). (5) Embedding rows are derived data: the deploy-time `pg_dump` excludes their table data and the backfill rebuilds it; the vector column sizes are fixed by migration 017, so a model with other dimensions needs a new migration. (6) Embeddings include private items on purpose (they never leave the machine; only the LLM is gated). (7) The backend enqueues are best-effort (`embeddings/enqueue.ts`): ML down never fails OCR, summary or thumbnail jobs, and `ML_URL` unset turns the whole thing off. (8) PaddleOCR shares the GPU with reverie-ml: the prod backend sets `FLAGS_allocator_strategy=auto_growth` and `FLAGS_gpu_memory_limit_mb` (inherited by the OCR subprocess through `...process.env`); `Dockerfile.ocr-base` must not be touched for this (hash-triggered multi-GB rebuild).
- `2026-11-20` — **Privacy is per private folder, there is no document flag and no global vault.** A document is private exactly when its folder or collection is (`documents.is_private` was dropped in migration 016). The lock unit is a private collection (covers its folders) or a private folder in a public collection; `services/privacy.ts loadLockMap` maps every folder to its lock id (trash ignored, so a trashed private folder stays private), and the open locks live in the httpOnly session cookie `vault_session` (JWT with `locks: string[]`, re-signed on each `POST /vault/unlock {password, folder_id}`, cleared on logout; no table or Redis). Rules to keep: (1) private documents never leave their folder, locked or not: every listing, search, facet, suggestion, count, tool and the LLM exclude them through `excludePrivateDocuments`/`getPrivateFolderIds`; (2) every per-document route calls `loadOpenDocument` (`services/document-access.ts`) and every folder-scoped route uses `FolderLocks.assertOpen`, answering 403 `FOLDER_LOCKED`; (3) signed `/files/*` URLs and thumbnail paths are produced only after that check, because `/files/*` verifies a signature, not the lock; (4) the vault JWT carries a `scope`, and `fastify.authenticate` and the socket handshake reject any scoped token, so the cookie can never be replayed as a bearer; (5) realtime `job:complete`/`job:failed` for a private document drop `result` and `error_message` (`toDeliverableEvent`); (6) `documents.folder_id` is ON DELETE SET NULL, so purging a private folder purges its trashed documents first, and trashing one keeps its documents in it (never the root). Users without an account password cannot lock anything: nothing is locked for them, but private documents still stay out of listings, search and tools. Deploy order is new code first, migrate after, so code must never reference the dropped column. Android keeps a read-only `is_private` per document for the build already installed.

- `2026-07-17` — **LLM name hallucinations leak into free-text, not just entities.** Diagnosed on prod doc `e32b273f...`: PaddleOCR read "TIETOENATOR" correctly (97% conf), entity grounding kept it correct, yet the model still wrote "Tietonenator" in the _summary_ and a _tag_. - `2026-11-19` — **`/mcp` and API tokens.** `/mcp` (`app/routes/mcp.route.ts`) is stateless Streamable HTTP: a fresh `Server` + `StreamableHTTPServerTransport({ sessionIdGenerator: undefined, enableJsonResponse: true })` per POST, answered through `reply.hijack()`; GET/DELETE are 405. Auth is deliberately split: `/mcp` accepts only `rvr_…` API tokens (`plugins/api-token-auth.ts`, SHA-256 hash looked up in `api_tokens`, revocation checked on every request, no cache), the JWT routes accept only JWTs — a leaked token cannot reach settings, the vault or `/api-tokens`. `api_tokens.kind` + `expires_at` are the seam for the later short-lived admin/agent token (`createApiToken(userId, name, { kind: 'agent', expiresAt })`; `listApiTokens` shows only `kind='personal'`). Rate limit: `/mcp` replaces the global per-IP bucket with 300/min keyed by sha256 of the bearer token (behind nginx every client shares one IP); inert in development like the other overrides. - `2026-11-19` — **In-app agent** (admin only): backend `src/agent/*` POSTs `{prompt, sessionId, mcpToken}` to the `reverie-agent` container (`apps/agent/server.mjs`, stock `claude -p`), relays NDJSON over Socket.io `agent:event`, stores chats in `agent_chats`/`agent_messages` (migration 015). Gotchas: `--tools ""` turns off built-ins but NOT MCP tools, so the args also use `--allowedTools mcp__reverie__*` + `--permission-mode dontAsk` (args are asserted in `agent.e2e.test.ts`). The shared secret is created by the BACKEND (root) in the `agent_secret` volume and mounted read-only in the agent, which re-reads it per request (inverted ownership avoids a volume-permission race and a manual setup step). No `depends_on` backend→agent on purpose: a fresh deploy must work before login. `authenticateAdmin` lazily imports `db/kysely`, which races `vi.mock` under concurrent `inject` calls: call it sequentially in tests. Signed-out claude emits an assistant message with `error: "authentication_failed"` then a `result` with `is_error`. `claude auth status --json` gives `{"loggedIn":bool}`. On macOS `sed -i ''`; Yarn needs `YARN_GLOBAL_FOLDER` in a sandbox.
- `2026-11-01` — **Merging (any push) to `main` is a production deploy**: `.github/workflows/deploy.yml` runs on every push to main and resets the home server to it (`git reset --hard origin/main` + `scripts/deploy.sh`, migrations included). There are no PR checks, so lint, typecheck, tests and review before merge are the only gate. So a migration must stay compatible with the running code and be reversible.
- `2026-11-20` — **Content-hash duplicate check** (`POST /documents/check-content`, `services/content-check.ts`; the old `check-duplicates` stays for the phone's installed build). It never reveals a private match: privacy comes from `loadLockMap` (trash ignored, so lock state and trashed-in-private don't change the answer), and private/trash rows contribute no id, name, path or filename — a test scans the serialized response for them. Results come back in input order; `name_conflict` means any live same-name document in the target folder, whatever its content. The hash is of the raw uploaded bytes (= `documents.file_hash`): web streams it in 8 MiB chunks through hash-wasm in a classic (iife) worker, since a module worker can't load over `file://` in production Electron; Android's `ContentHasher` and `UploadStager` share `openOriginal` (`setRequireOriginal` for images) so both hash the same bytes. Folder paths are joined from current names, not the stale `folders.path`.
- `2026-11-20` — **Android auto-backup** (`data/backup/`, Room v6 `backup_ledger` + `backup_retry`). The ledger lives in `reverie.db`, which still has `fallbackToDestructiveMigration()` for a version jump without a migration: every future schema bump needs a real `Migration`, or the ledger is wiped and the next pass re-hashes every photo and video in the chosen albums (costly, not unsafe, since `check-content` still skips what's in the library). `Migration5To6` SQL is copied from the generated `ReverieDatabase_Impl` (schema isn't exported); a mismatch crashes on open. `BackupWorker` is a plain worker that always returns success (failure lives in settings + `backup_retry`, so WorkManager never applies its own backoff); `BackupRunner` holds a process-wide lock (background passes give up, "Back up now" waits). A background run is killed after ~10 minutes and the backend has no resumable upload, so a video that can't finish in one slice is parked ("needs the app open") and finished by a foreground "Back up now". `AuthSessionManager.bootstrap()` is only called from the UI, so a background worker must call it itself. In a sandbox without write access to `~/.yarn`, `yarn install` fails with EPERM: run it with `YARN_GLOBAL_FOLDER` pointing at a writable dir (a copied `node_modules` can predate dependencies and break typecheck).
- `2026-11-21` — **torch's default Linux wheel vs the server's driver.** PyPI's `torch` for Linux x86_64 is built for the newest CUDA (13.2 for 2.15.0), but the home server's driver is 535 (CUDA 12.2) and runs only CUDA 12.x builds (minor-version compatibility, driver >= 525); with a mismatch `torch.cuda.is_available()` is False with "NVIDIA driver ... too old" and reverie-ml silently runs on the CPU. `apps/reverie-ml/requirements.txt` therefore pins `torch==2.14.1+cu126` from `download.pytorch.org/whl/cu126` under a Linux x86_64 marker (2.14.1 is the newest torch with a CUDA 12.x Linux wheel; cu129 stops at 2.13.0), and the Docker build runs `python -m app.runtime`, which fails unless `torch.version.cuda` starts with `12`. Pitfalls: `torch==2.14.1` also matches `2.14.1+cu126`, so the non-Linux fallback line uses `===`; pip evaluates markers against the host, not `--platform`, so check the Linux line with `uv pip compile --python-platform x86_64-manylinux_2_28`. Before bumping torch or the driver, re-check which CUDA the new wheel is built for.
