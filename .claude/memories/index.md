- `2026-11-21` — **HLS serving/playback (`storage/hls-token.ts`, `utils/serve-stored-file.ts`, `video-viewer/useHlsSource.ts`) gotchas.** (1) One path token `/files/hls/{exp}/{sig}/{hash}/…` covers a whole transcode set because a playlist's segment URLs are relative: sig is md5 over `$exp/hls/$hash$secret`, and nginx and the dev route must both agree (the nginx `location` is applied by hand on the server). (2) The dev route must not set its own CORS: the global `@fastify/cors` plugin already answers, and a second header overwrites it. (3) `sendStoredFile` sends an object body, so its 404 needs an explicit `application/json` content type or Fastify 500s after a binary type was set. (4) Playwright's headless shell has no H.264, so browser checks of the ladder use a VP9 fMP4 set with the same layout. (5) hls.js keeps the old token in its loaded playlists: a 403/410 on a playlist or fragment means refetch the document and rebuild the player at the current time, not fall back to the original (signed at the same moment, so it has expired too). (6) Media3's `media3-exoplayer-hls` needs the same version as `media3-exoplayer`; Gradle offline mode fails until one online fetch.
- `2026-11-21` — **Video transcoding (`transcode/`, `workers/transcode.worker.ts`) gotchas.** (1) The BullMQ job id of a transcode job is the `processing_jobs` row's UUID (`queueTranscode` inserts the row first): the job events schema requires a UUID `job_id`, and `processJobWithTracking` updates the row by `job.id`. (2) Renditions live under `transcode/<file_hash>/` and are shared by identical uploads; `transcode_sets.files` is the only list of what is stored (the storage providers cannot list or delete a prefix), the row is written after every file, and `deleteTranscodeSetIfUnused` runs on purge (and after an encode, in case the last document was purged meanwhile); trash keeps the set. (3) ffmpeg's `-color_primaries/-color_trc/-colorspace` output flags do not retag frames: every chain ends in `setparams=…bt709…`, which is what makes ffprobe report BT.709. ffmpeg autorotate (the default) applies the rotation and drops the display matrix, so never add a `transpose`. (4) ffmpeg 8 names the HLS init file `init_<n>.mp4` whatever `-hls_fmp4_init_filename` says, so output files are found by walking the output dir, never by name. (5) The dev ffmpeg has no `zscale` (libzimg): `hdr-filters.ts` then tone maps with `lutrgb` + `colorchannelmixer` + `tonemap` (`tonemap` alone cannot read HLG/PQ); `colorchannelmixer` coefficients are limited to ±2, hence the gain stages. The PQ lookup is exact up to 625 nits and clips above. NVENC and zscale on the prod container's ffmpeg (Debian apt, 5.1) are not verified from a dev machine: the worker logs the detected capabilities at start. (6) The backfill is one job with a fixed id, rescheduled with `moveToDelayed` + `DelayedError`, at priority 10, and only queues work while OCR, thumbnail, LLM and other transcode queues are empty (`isTranscodePipelineBusy`): a video is found again after a restart because the cursor is only an optimisation, the query is `transcode_status = 'pending'` and no live job. (7) `@reverie/shared` is consumed from its `dist`: after changing the job event schemas run `nx run @reverie/shared:build` before the backend typecheck or tests.
- `2026-11-21` — **The image call (`llm/image-understanding.ts`, `image-call.ts`, `image-look.ts`) replaced `processVisionDocument`.** (1) `decideImageLook` is the one gate, run again when the LLM job runs (not when it is queued): non-image, `isHeldBackFromVision` (camera evidence, `photo` category or verdict), then a stored verdict must map to screenshot/document/receipt/diagram, else no call. No verdict means no call whatever the category and whether or not reverie-ml is up (the OCR heuristics call a phone photo a screenshot); the image is held back and the backfill picks it up once a verdict exists. A lone capture date holds an image back unless a stored verdict decided the category (the OCR heuristics call a phone-sized photo a screenshot). (2) The image goes out as JPEG, 1568 px long edge, re-encoded by sharp (so EXIF/GPS never leave); the call's schema has no `photo` kind, so the kind cannot move to or from photo, and `toCategoryAfterLook` maps the answer to a category. (3) The call runs whatever the OCR says; grounding and spelling correction of the model's entities run only when the OCR is reliable (`isReliableOcr`), because correcting against garbage OCR would damage right answers. (4) Old `llm_results.processing_type = 'vision_describe'` rows and queued jobs still exist: they are readable and routed to the image call; the backfill (`understand` stage in `embeddings/backfill.ts`, `llm/understand-backfill.ts`) replaces them, 5 per page, skipping documents whose job failed in the last 24 h. (5) A failed run keeps an existing summary (`markLlmFailed` in `llm/llm-store.ts`). (6) `LLM_VISION_ENABLED` gates the whole call (default false) when the job runs as well as when it is queued: with it off, a job that already carries `image_understanding` or `vision_describe` takes the text-summary path.
- `2026-11-21` — **Meaning search keeps a hit only above a per-query cutoff taken from the library's own noise (`search/semantic-noise.ts`).** The fixed floors of the first version (text 0.53, image 0.17) cut away most real matches: real image-stream hits score 0.10–0.17 (siglip2 text→image), real text hits 0.45–0.66 (bge-m3), and a query with nothing in the library ("lumi talvi") tops out near 0.39 on text. Rule per query and stream: cutoff = max(absolute minimum, median + z·sigma), where median and sigma (IQR/1.349, robust to the real matches in the tail) come from the query's similarity to a fixed deterministic sample (≤5000, text ordered by a per-chunk hash so long documents cannot fill it, images by document hash) of the user's embeddings of that model, and z = sqrt(2 ln N) + margin: the best of N pure-noise draws sits about sqrt(2 ln N) sigmas out, so a fixed z lets more noise through as the library grows; the margin covers tails heavier than a normal (a Student-t simulation leaked the plain bound for most no-match queries, ~5% at +1.5). Knobs: `SEMANTIC_{TEXT,IMAGE}_MIN_SIMILARITY` (0.35 / 0.06) and `SEMANTIC_{TEXT,IMAGE}_MARGIN_Z` (1.5); they replace the old `*_FLOOR` pair. Gotchas: the stats ignore the query's filters, private folders and the agent guard on purpose (the cutoff must not move when a folder is unlocked); under 50 embeddings only the absolute floor applies; tests that need a hit to survive set `marginZ: -Infinity` (absolute floor only). `similar_to` (image-to-image, scale 0.4–0.95) never goes through this. Known limit: a broad query that matches a large share of the library ("screenshot" in a screenshot-heavy library) raises the median and widens sigma, so the meaning stream keeps little and full text answers. To tune on real data run `semantic-probe.js "query" ...` (prod container, cwd `apps/backend/dist`, see the script header): it prints per stream the noise stats, the cutoff, and kept/dropped hits with filenames only.

(4) Every vector query starts from `applySearchFilters` (the agent passes a guarded base that also drops withheld photos), so private, trashed and foreign rows can never come back through a vector stream; a new vector path must do the same. - `2026-11-21` — **Embeddings (pgvector + `reverie-ml` + `embed-queue`) gotchas.** (1) Postgres stays Alpine/musl: `docker/postgres/Dockerfile` builds pgvector onto the pinned `postgres:16.x-alpine3.y`; never switch to the Debian `pgvector/pgvector` image (glibc over a musl-made data dir silently changes collation). (2) BullMQ rejects `:` in custom job ids, and `queue.add` with a job id that still exists is silently dropped, so the backfill (`embed-backfill`) reschedules the same job with `updateData` + `moveToDelayed` + `throw new DelayedError()` rather than adding a successor. (4) The repo's `NonRetryableJobError` does not stop BullMQ retries; use `UnrecoverableError` for a final failure (an undecodable image). (5) Embedding rows are derived data: the deploy-time `pg_dump` excludes their table data and the backfill rebuilds it; the vector column sizes are fixed by migration 017, so a model with other dimensions needs a new migration. (6) Embeddings include private items on purpose (they never leave the machine; only the LLM is gated). (7) The backend enqueues are best-effort (`embeddings/enqueue.ts`): ML down never fails OCR, summary or thumbnail jobs, and `ML_URL` unset turns the whole thing off. (8) PaddleOCR shares the GPU with reverie-ml: the prod backend sets `FLAGS_allocator_strategy=auto_growth` and `FLAGS_gpu_memory_limit_mb` (inherited by the OCR subprocess through `...process.env`); `Dockerfile.ocr-base` must not be touched for this (hash-triggered multi-GB rebuild).
- `2026-11-20` — **Privacy is per private folder, there is no document flag and no global vault.** A document is private exactly when its folder is private or sits beneath a private one, at any depth (`documents.is_private` was dropped in migration 016). The lock unit is the outermost private folder (it covers everything beneath it); `services/privacy.ts loadLockMap` maps every such folder to its lock id (trash ignored, so a trashed private folder stays private), and the open locks live in the httpOnly session cookie `vault_session` (JWT with `locks: string[]` and `gen`, re-signed on each `POST /vault/unlock {password, folder_id}`, cleared on logout; which locks are open is in no table and not in Redis). Rules to keep: (1) private documents never leave their folder, locked or not: every listing, search, facet, suggestion, count, tool and the LLM exclude them through `excludePrivateDocuments`/`getPrivateFolderIds`; (2) every per-document route calls `loadOpenDocument` (`services/document-access.ts`) and every folder-scoped route uses `FolderLocks.assertOpen`, answering 403 `FOLDER_LOCKED`; (3) signed `/files/*` URLs and thumbnail paths are produced only after that check, because `/files/*` verifies a signature, not the lock; (4) the vault JWT carries a `scope`, and `fastify.authenticate` and the socket handshake reject any scoped token, so the cookie can never be replayed as a bearer; (5) realtime `job:complete`/`job:failed` for a private document drop `result` and `error_message` (`toDeliverableEvent`); (6) `documents.folder_id` is ON DELETE SET NULL, so a folder purge deletes the documents of the whole subtree before the folder rows (see the 2026-11-25 entry on nested folders). **What opens a lock** is the user's lock secret (a 4-digit PIN or a password of its own, `folder_lock_secrets`, migration 030, read and written only by `services/lock-secret.ts`), or the account password when none is set or ten wrong tries have stopped it; the status' `ask` says which, and `password` in the unlock body is checked against that one secret only. (7) A try is taken in one `UPDATE … WHERE wrong_tries < 10` before any hash is compared and given back only to the try that was right; a right lock secret never resets the count (someone holding a session would get fresh guesses from each of the owner's unlocks), only the account password does, given at a stopped lock or when saving a secret; wrong account passwords are not counted, so nobody can be locked out for good. (8) Counted refusals and a wrong account password on `PUT /vault/secret` are 403, never 401: the web and Android clients answer a 401 by refreshing the login and resending, which would spend a second try and can sign the user out. Only the unlock with no secret set keeps its old 401. (9) Every save bumps `generation` (removing keeps the row, so it never goes back) and the cookie's `gen` must equal it (none counts as 0), which closes every session's open locks; the saving session gets a fresh cookie. (10) What is typed must not reach a log: the global error handler answers the JSON parser's `SyntaxError` (it quotes the body) with a static 400 and logs nothing, and both secret columns are always written together because Postgres quotes the row in a constraint error. Users without an account password cannot lock anything: nothing is locked for them, but private documents still stay out of listings, search and tools. Deploy order is new code first, migrate after, so code must never reference the dropped column. Android keeps a read-only `is_private` per document for the build already installed.

## MCP upload

- `2026-11-26` — **Files arrive from MCP through curl, not through tool calls** (`tools/upload-command.ts`, `POST /mcp/upload`, one-time link in Redis). (1) curl percent-encodes `"` in a multipart filename unless `--form-escape` (curl 7.81+), and the server would store the encoded name; the multipart parser cuts a filename at a backslash, so such paths are refused. (2) curl labels `.md`, `.csv` and others `application/octet-stream`, so the upload service's extension-to-MIME map decides whether text is extracted and a thumbnail made: a new file format needs its extension there too. (3) The test world's seeded `storage_path` is absolute and the local storage provider refuses it: a test that really stores files sets a relative one.

## Server errors

- `2026-11-26` — **A route's 4xx response schema also has to fit what `error-handler.ts` answers with that status** (`{statusCode, error, message}`, plus `details` after a failed validation): a broken body, a rate limit or a failed schema reaches any route. A schema the envelope does not fit, an enum of error codes for one, or one the zod serializer cannot read (raw JSON Schema) turns that answer into a 500. Use `RouteErrorSchema` where a route also sends its own `{error, message}`. The handler passes a 4xx error's message on to the client, so an error whose message quotes the request must be given static text there, as the body parser's `SyntaxError` is.
